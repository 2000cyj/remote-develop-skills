## 四、BUG-001 店铺导出「关联主体」列未做合并行处理

### 4.1 现象
`店铺信息_导出_*.xlsx` 中，关联同一主体（如「test公司」）的相邻店铺行，其「关联主体」列每个单元格都单独填值，没有任何合并单元格。

### 4.2 根因分析（已核验）

导出调用链：`StoreController.exportStore` → `StoreManageServiceImpl.exportStore` → `ExcelExportService.exportExcel` → `ExcelExportUploadExecutor`（异步线程）→ `ExcelTempFileExportUtil.writeTempFile` → EasyExcel 写 Sheet。

1. `StoreManageServiceImpl.exportStore`（L167-175）已**把同一主体的行排到相邻**：
   ```java
   // 8. 以全字段店铺为准，按关联主体相邻排序（主体信息合并行的近似处理，异步导出框架不支持物理合并单元格）
   exportStoreList.sort(Comparator
           .comparing((Store s) -> s == null || s.getCompanyName() == null ? "" : s.getCompanyName())
           .thenComparing(s -> s == null || s.getStoreCode() == null ? "" : s.getStoreCode()));
   ```
   注释明确写了"异步导出框架不支持物理合并单元格"——**实现方已知需求要合并、但框架不支持，只能先排序近似处理**，即测试结论成立。

2. `StoreExportVO` 中「关联主体」为第 2 列（`@ExcelProperty("关联主体") private String companyName`，**列索引 = 1**）。

3. `ExcelTempFileExportUtil.writeHeadSheet`（L349-353）写 Sheet 时只注册了样式策略，**未注册任何合并 WriteHandler**：
   ```java
   WriteSheet writeSheet = EasyExcel.writerSheet(defaultSheetName(exportDataDTO.getSheet_name(), sheetIndex))
           .head(head)
           .registerWriteHandler(styleStrategy)
           .build();
   excelWriter.write(tableDataList, writeSheet);
   ```

4. `ExcelExportDataDTO` 只有表头/样式/图片/链接等字段，**没有"合并列"配置项**，导出方无法表达"第 N 列按相邻同值合并"的意图。

5. bi-core 已有 `ExcelMergeCellExporter`（POI 直接导出，支持 `sameValueMergeTitles` 同值合并），但它是**同步、直连 HTTP 响应**的导出路径，与出纳所用的"异步生成 + 上传下载中心"路径（`ExcelExportService`）不是同一套。

### 4.3 解决方案

推荐 **方案 A**：给异步导出框架（bi-core `bi-starter-excel`）增加"按列合并相邻同值单元格"能力，店铺导出传入「关联主体」列索引即可。通用、影响面小、其它导出后续可复用。

**方案 A 具体改动（4 处）：**

**A-1** `ExcelExportDataDTO` 新增合并列配置字段：
```java
@ApiModelProperty("按列纵向合并相邻相同值：指定列的 0-based 列索引集合")
private List<Integer> sameValueMergeColumns;
```

**A-2** 新建合并 WriteHandler（`bi-core/bi-starter-excel`，与 `ExcelTempFileExportUtil` 同包）：
```java
package com.obo.core.excel.export;

import com.alibaba.excel.write.handler.CellWriteHandler;
import com.alibaba.excel.write.metadata.holder.WriteSheetHolder;
import com.alibaba.excel.write.metadata.holder.WriteTableHolder;
import org.apache.poi.ss.usermodel.Cell;
import org.apache.poi.ss.usermodel.Row;
import org.apache.poi.ss.usermodel.Sheet;
import org.apache.poi.ss.util.CellRangeAddress;

import java.util.List;

/**
 * 按列纵向合并相邻且值相同的单元格。
 * 在整张 Sheet 写完的最后一个非表头单元格回调时扫描目标列，合并连续相同值的区间。
 */
public class SameValueMergeWriteHandler implements CellWriteHandler {

    private final List<Integer> mergeColumns;
    private final int startRow;  // 数据首行（跳过表头）
    private boolean executed = false;

    public SameValueMergeWriteHandler(List<Integer> mergeColumns, int headerRowCount) {
        this.mergeColumns = mergeColumns;
        this.startRow = headerRowCount;
    }

    @Override
    public void afterCellDispose(WriteSheetHolder writeSheetHolder,
                                 WriteTableHolder writeTableHolder,
                                 List<com.alibaba.excel.metadata.data.WriteCellData<?>> cellDataList,
                                 Cell cell,
                                 Boolean isHead,
                                 Boolean isEmpty) {
        if (Boolean.TRUE.equals(isHead) || executed) {
            return;
        }
        Sheet sheet = writeSheetHolder.getSheet();
        int lastRowNum = sheet.getLastRowNum();
        for (int col : mergeColumns) {
            mergeColumn(sheet, col, startRow, lastRowNum);
        }
        executed = true;
    }

    private void mergeColumn(Sheet sheet, int col, int startRow, int endRow) {
        int segStart = startRow;
        String last = cellString(sheet, segStart, col);
        for (int r = segStart + 1; r <= endRow; r++) {
            String cur = cellString(sheet, r, col);
            if (!cur.equals(last)) {
                if (segStart < r - 1) {
                    sheet.addMergedRegion(new CellRangeAddress(segStart, r - 1, col, col));
                }
                segStart = r;
                last = cur;
            }
        }
        if (segStart < endRow) {
            sheet.addMergedRegion(new CellRangeAddress(segStart, endRow, col, col));
        }
    }

    private String cellString(Sheet sheet, int rowIdx, int colIdx) {
        Row row = sheet.getRow(rowIdx);
        if (row == null) {
            return "";
        }
        Cell c = row.getCell(colIdx);
        return c == null ? "" : (c.getStringCellValue() == null ? "" : c.getStringCellValue());
    }
}
```

**A-3** `ExcelTempFileExportUtil.writeHeadSheet` 在 `WriteSheet` 上注册该 Handler（仅在传入合并列时生效，向后兼容）：
```java
List<Integer> mergeColumns = exportDataDTO.getSameValueMergeColumns();
if (CollUtils.isNotEmpty(mergeColumns)) {
    writeSheet.registerWriteHandler(new SameValueMergeWriteHandler(mergeColumns, head.size() /* 表头行数 */));
}
```
（当前出纳导出均为单级表头，`head.size()` = 表头行数 1；若未来多级表头需相应调整。）

**A-4** `StoreManageServiceImpl.exportStore` 组装导出数据时传入「关联主体」列索引 1：
```java
ExcelExportDataDTO exportData = ExcelExportDataDTO.builder()
        .clazz(StoreExportVO.class)
        .sheet_name("店铺信息")
        .dataList(rowList)
        .sameValueMergeColumns(Collections.singletonList(1)) // 关联主体（companyName）第 2 列
        .build();
```

> **备选方案 B**：直接用 bi-core 已有的 `ExcelMergeCellExporter`（`SheetRequest.sameValueMergeTitles = ["关联主体"]`）生成 xlsx 字节流，再复用下载中心上传逻辑。但它不在 `ExcelExportService` 异步框架内，需在 `StoreManageServiceImpl` 内自建临时文件 + `MinioFileUploadExecutor` 上传，绕过通用框架，维护成本高，不推荐。

### 4.4 改动清单与验证
- 后端 bi-core：`ExcelExportDataDTO` + 新增 `SameValueMergeWriteHandler` + `ExcelTempFileExportUtil`（框架通用能力，其它模块导出可复用）。
- 后端 bi-cashier：`StoreManageServiceImpl`（传列索引）。
- 验证：`pnpm dev:local` 起 cashier，店铺管理导出，打开 xlsx 确认同一主体相邻行的「关联主体」列已合并为单个单元格（合并后保留左上角值）。

## 五、BUG-002 公司导出缺少「开票资料」文件列

### 5.1 现象
`公司信息_导出_*.xlsx` 文件类列表头只有 17 列（身份证正反面拍照 → 其他资质证明），缺少「开票资料」。

### 5.2 根因分析（已核验）

公司导出的文件列**不是硬编码的，而是由标签库驱动**：

`CompanyManageServiceImpl.exportCompany` L319-325：
```java
// 8. 加载公司文件标签（从标签库取 system 标签，按 sortOrder 排序）
List<FileTagLibrary> tagLibList = fileTagLibraryService.listEnabledTagsByModuleAndType(SourceModuleEnum.COMPANY_FILE_LIST, "system");
List<String> companyTagList = tagLibList.stream()
        .filter(Objects::nonNull)
        .map(FileTagLibrary::getTagName)
        .filter(Objects::nonNull)
        .collect(Collectors.toList());
```
表头列与文件匹配标签均来自 `cashier_file_tag_library`（`variable_code='company_file_list'` 且 `tag_type='system'`），查询逻辑见 `FileTagLibraryServiceImpl.listEnabledTagsByModuleAndType` L47-58。

`docs/sql/bi-cashier-all.sql`（L236-253）种子数据只预置了 **17 个 system 标签**，全库检索不到「开票资料」：
```
身份证正反面拍照 / 法人手持身份证正反面拍照 / 身份证复印件 / 注册地址租赁合同 / 房产证复印件 /
产权证明 / 准允开业通知书 / 营业执照正本原件扫描件 / 营业执照副本原件扫描件 / 法人手持营业执照正本 /
法人手持营业执照副本 / 生产许可证 / 开户许可证 / 持有商标 / 变更资料 / 条码证 / 其他资质证明
```

需求文档口径冲突（与测试文档记录一致）：3.1.1「导出字段映射」「文件标签匹配规则」均列出 18 类（含「开票资料」），而「需求范围」第 1 条写"17 种文件类型"。**当前实现与明细表（18 类）不一致**。

### 5.3 解决方案

1. **先与需求方确认口径**（17 种 vs 18 类），并确认「开票资料」标签的匹配规则与文件类型。
2. 若确认补「开票资料」（18 类），向标签库补一条 system 标签（按现有排序，`sort_order=18`）：
   ```sql
   INSERT INTO cashier_file_tag_library
       (tag_name, tag_type, status, sort_order, create_user, variable_code)
   VALUES
       ('开票资料', 'system', 1, 18, 'system', 'company_file_list');
   ```
   同时同步 dev / test / pre / prod 各环境。
3. **无需改后端代码**：标签库一旦启用该标签，`listEnabledTagsByModuleAndType` 自动返回，导出即自动多出「开票资料」列；历史已上传且 `tag_name_list` 含「开票资料」的文件也会自动匹配进该列。

> 注意：标签库是全模块共享的数据源，前端公司文件管理（新增/编辑文件弹窗的标签下拉，走 `/listCompanyFileTags`）也会随之出现「开票资料」选项，属预期行为。若需求方最终明确维持 17 种，则无需改动，关闭本 Bug。

### 5.4 改动清单与验证
- 数据（SQL）：`cashier_file_tag_library` 新增「开票资料」system 标签（按需求口径确认后执行）。
- 验证：公司管理导出，确认文件列数为 18 列且含「开票资料」；有「开票资料」标签文件的公司该列出现下载链接。

## 六、BUG-003 公司导出「所属部门」导出为字典原始码

### 6.1 现象
导出「所属部门」列填的是 `11`、`11，121，122` 等原始字典 ID；列表页同一条数据显示「市场部」「市场部、电商一部、电商二部」。

### 6.2 根因分析（已核验，含对测试文档"疑似原因"的更正）

列表页能显示中文，是因为**前端用字典翻译**（`src/pages/company/config/index.ts` L159-165）：
```ts
formatter: ({ row }) => {
  const ids: string[] = (row.departmentIdList || []).map((v: string) => String(v))
  const names = ids
    .map(id => CASHIER_BELONGS_DEPARTMENT.list.find(d => d.one_id === id)?.one_name)
    .filter(Boolean)
  return names.length ? names.join("、") : "-"
}
```
列表页能翻对，说明 **`CASHIER_BELONGS_DEPARTMENT` 字典实际已配置**（至少 `one_id/one_name` 有数据）。

后端导出**根本没有做字典翻译**，直接 `String.join` 原始 ID：

`CompanyManageServiceImpl.exportCompany` L311-314 加载的字典集合**不含 `CASHIER_BELONGS_DEPARTMENT`**：
```java
Map<String, Map<String, String>> dictMap = CashierExportUtils.loadDictLabelMap(dataDictionaryProvider, Arrays.asList(
        DictTypeConstants.CASHIER_COMPANY_STATUS, DictTypeConstants.CASHIER_COMPANY_ATTRIBUTION_TYPE,
        DictTypeConstants.CASHIER_BUSINESS_STATUS, DictTypeConstants.CASHIER_TAX_STATUS,
        DictTypeConstants.CASHIER_TAXPAYER_TYPE, DictTypeConstants.CASHIER_ARCHIVE_STATUS, DictTypeConstants.CASHIER_TAX_PERIOD));
```

L454-455 直接拼接原始 ID：
```java
row.put("department_id_list", CollUtils.isEmpty(company.getDepartmentIdList()) ? ""
        : String.join("，", company.getDepartmentIdList()));
```

> ⚠️ **测试文档"疑似原因"更正**：测试文档写"导出逻辑使用字典 CASHIER_BELONGS_DEPARTMENT 翻译失败（该字典为空/未配置），回退成了原始码"。**实际代码显示：公司导出从未把 `CASHIER_BELONGS_DEPARTMENT` 加入字典加载集合，也从未对该列调用 `translate`，不存在"翻译失败回退"路径**——是"根本没翻译"。同时该字典并未为空（列表页依赖它渲染中文），因此补上字典加载与翻译即可修复。

对照参考：**员工导出已正确处理**该字典（`EmployeeManageServiceImpl.exportCashierEmployee` L383-398）：
```java
Map<String, Map<String, String>> dictMap = CashierExportUtils.loadDictLabelMap(dataDictionaryProvider,
        Arrays.asList(DictTypeConstants.CASHIER_BELONGS_DEPARTMENT, DictTypeConstants.CASHIER_DEPARTMENT_PROPERTIES));
...
row.setCashierDepartmentName(StringUtils.isNotEmpty(vo.getCashierDepartmentName())
        ? vo.getCashierDepartmentName()
        : CashierExportUtils.translate(dictMap, DictTypeConstants.CASHIER_BELONGS_DEPARTMENT, vo.getCashierDepartment()));
```

## 七、BUG-004 公司导出「费用归属负责人」导出占位符文本

### 7.1 现象
「费用归属负责人」列出现 `待更新字典（CASHIER_BELONGS_DEPARTMENT）1`、`…2` 等占位符文本。

### 7.2 根因分析（已核验，含对测试文档"疑似原因"的更正）

「费用归属负责人」的取值链路：

1. **前端保存时从字典 `two_id` 推导**（`src/pages/company/addOrEdit/add.vue` L695-701，`editOrCheck.vue` L638-644 相同）：
   ```ts
   // 所属部门联动（多选）：费用归属负责人取所选部门的 two_id
   watch(() => formData.departmentIdList, (vals) => {
     formData.feeOwnerList = (vals || [])
       .map(v => CASHIER_BELONGS_DEPARTMENT.list.find(d => d.one_id === v)?.two_id)
       .filter((x): x is string => Boolean(x))
   }, { deep: true })
   ```
   即：`feeOwnerList` = 所选所属部门对应字典项的 `two_id`。

2. 后端把 `feeOwnerList` 原样存库：`cashier_company.fee_owner_list`（`Company` 实体 L120-122，`StringListTypeHandler` 存 JSON 数组）。

3. 导出原样透出：`CompanyManageServiceImpl.exportCompany` L456-457：
   ```java
   row.put("fee_owner_list", CollUtils.isEmpty(company.getFeeOwnerList()) ? ""
           : String.join("，", company.getFeeOwnerList()));
   ```

> ⚠️ **测试文档"疑似原因"更正**：测试文档写"代码的字典翻译兜底逻辑把「字典名+序号」当成了显示文本"。**实际代码核对：后端全库 `grep 待更新字典` 无任何命中，不存在这种兜底逻辑**。占位符文本的真实来源是**字典数据**：`CASHIER_BELONGS_DEPARTMENT` 各字典项的 `two_id` 字段被配置成了 `待更新字典（CASHIER_BELONGS_DEPARTMENT）N`（测试/开发环境字典模板数据），前端取它当费用归属负责人保存，导出透出。因此这是**字典数据问题 + 前端 `two_id` 推导保存的组合结果，不是导出层制造**。

### 7.3 解决方案

**① 根因：修正字典数据（字典服务库 `data_dictionary` 表）**

将 `CASHIER_BELONGS_DEPARTMENT` 各字典项的 `two_id` 配置为真实的「费用归属负责人」值（负责人姓名或人员唯一标识，按业务口径），清除占位符：
```sql
-- 先核对当前占位数据
SELECT one_id, one_name, two_id FROM data_dictionary
 WHERE type_id = 'CASHIER_BELONGS_DEPARTMENT';
-- 逐项修正 two_id（示例：one_id='11' → two_id='张三'）
UPDATE data_dictionary SET two_id = '张三'
 WHERE type_id = 'CASHIER_BELONGS_DEPARTMENT' AND one_id = '11';
-- 校验占位符清零
SELECT COUNT(*) FROM data_dictionary
 WHERE type_id = 'CASHIER_BELONGS_DEPARTMENT' AND two_id LIKE '%待更新字典%';
```

**② 存量数据回填（已保存占位符的公司）**

即使字典修好，已入库 `cashier_company.fee_owner_list` 仍是占位符，需按 `department_id_list` → 字典 `two_id` 重新生成（MySQL 8）：
```sql
-- 生成待回填清单（先核对）
SELECT c.unique_value, c.department_id_list, c.fee_owner_list
  FROM cashier_company c
 WHERE c.fee_owner_list LIKE '%待更新字典%';

-- 回填：按 department_id_list 重新映射 two_id 生成 fee_owner_list
UPDATE cashier_company c
   SET c.fee_owner_list = (
         SELECT JSON_ARRAYAGG(d.two_id)
           FROM JSON_TABLE(c.department_id_list, '$[*]' COLUMNS (dept_id VARCHAR(50) PATH '$')) jt
           JOIN data_dictionary d
             ON d.type_id = 'CASHIER_BELONGS_DEPARTMENT' AND d.one_id = jt.dept_id
          WHERE d.two_id IS NOT NULL AND d.two_id <> ''
       )
 WHERE c.fee_owner_list LIKE '%待更新字典%';
```
（若 `fee_owner_list` 存的是业务上不需要展示的 ID，则导出侧还需按字典 `two_id → 展示名` 翻译，见下方③可选。）

**③ 防御性加固（建议一并做）**

- 前端（`add.vue` / `editOrCheck.vue`）：联动生成 `feeOwnerList` 时过滤空 `two_id` 与占位符文本。注意需**拆成两个 filter**：`.map` 返回 `string | undefined`，类型守卫 `x is string` 只影响返回值类型，谓词内部 `x` 仍是 `string | undefined`，直接 `PLACEHOLDER_PATTERN.test(x)` 会报 TS2345；先过滤 undefined 窄化成 `string` 后再过滤占位符：
  ```ts
  const PLACEHOLDER_PATTERN = /待更新字典|测试数据/
  formData.feeOwnerList = (vals || [])
    .map(v => CASHIER_BELONGS_DEPARTMENT.list.find(d => d.one_id === v)?.two_id)
    .filter((x): x is string => Boolean(x))       // ① undefined 剔除，此时已窄化成 string
    .filter(x => !PLACEHOLDER_PATTERN.test(x))    // ② 此时 x 是 string，可安全 test
  ```
- 导出侧可选：若业务要求兜底，对含 `待更新字典` 的值置空（不建议为数据错误增加业务逻辑，仅作兜底）。

### 7.4 改动清单与验证
- 数据（SQL）：修正 `CASHIER_BELONGS_DEPARTMENT` 字典 `two_id` + 回填 `cashier_company.fee_owner_list`。
- 前端：`add.vue` / `editOrCheck.vue` 过滤占位符（防御）。
- 验证：公司管理 → 编辑某公司 → 重选所属部门 → 保存 → 导出，确认「费用归属负责人」为真实负责人姓名；历史公司导出不再出现占位符。

## 八、BUG-005 公司导出多个文件列填入了同一个文件下载链接

### 8.1 现象
同一公司的多个文件列（如「身份证正反面拍照」「法人手持身份证正反面拍照」「身份证复印件」）填入同一个 URL。

### 8.2 根因分析（已核验）

导出文件列匹配逻辑 `CompanyManageServiceImpl.exportCompany` L282-296：
```java
// 文件：按 (uniqueValue, tagName) → 第一个匹配的文件 URL
Map<String, Map<String, String>> fileUrlByUvAndTag = new java.util.HashMap<>();
for (FileExpiryRecord rec : fileRecordList) {
    ...
    if (CollUtils.isNotEmpty(rec.getTagNameList())) {
        for (String tag : rec.getTagNameList()) {
            if (StringUtils.isNotEmpty(tag) && StringUtils.isNotEmpty(rec.getFileUrl())) {
                fileUrlByUvAndTag.get(rec.getSourceUniqueValue()).putIfAbsent(tag, rec.getFileUrl());
            }
        }
    }
}
```

数据模型：`cashier_file_expiry_record` 中**一个文件记录（一行）的 `tag_name_list` 是一个 JSON 数组，可同时挂多个标签**（保存逻辑 `saveCompanyFileTags` L967 `rec.setTagNameList(fileItem.getTagNameList())` 整组存入）。

因此：**当同一个文件被挂了多个标签时，多个文件列自然填同一个 URL**（每个 tag 取该文件记录的首个匹配 URL，`putIfAbsent` 保证每列只取第一个）。这是"同一文件挂多标签"的数据语义，**若源数据确实如此，则导出行为符合需求，不是代码缺陷**（与测试文档"待核实"结论一致）。

### 8.3 解决方案：先核实源数据再定性

执行以下 SQL 定位"一个文件挂多个标签"或"同一 URL 出现在多个文件记录"的情况：

```sql
-- 1) 一个文件记录挂了多个标签（直接导致多列同 URL）
SELECT source_unique_value AS company_uv,
       un_name            AS file_id,
       file_name,
       file_url,
       tag_name_list
  FROM cashier_file_expiry_record
 WHERE source_module = 'company_file_list'
   AND JSON_LENGTH(tag_name_list) > 1;

-- 2) 同一个文件 URL 出现在多个文件记录（可能同一文件被传多次 / 多个 un_name 指向同一 http_path）
SELECT source_unique_value AS company_uv,
       file_url,
       COUNT(*) AS cnt,
       GROUP_CONCAT(un_name) AS file_ids
  FROM cashier_file_expiry_record
 WHERE source_module = 'company_file_list'
   AND file_url IS NOT NULL AND file_url <> ''
 GROUP BY source_unique_value, file_url
HAVING COUNT(*) > 1;
```

定性结论：
- 若第 1 条 SQL 命中"同一 `un_name` 的 `tag_name_list` 含多个标签"（如 gggggggggg 公司：身份证正反面拍照 + 法人手持 + 身份证复印件三个标签挂同一文件）→ **符合"同一文件挂多标签"的数据事实，导出无缺陷**，关闭本 Bug。
- 若出现"不同文件记录、URL 却相同"（`http_path` 相同但 `un_name` 不同）→ 需检查文件上传/去重流程（同一文件被重复上传），属上传侧问题。
- 若出现"每列本应独立文件、却被合并"→ 再复核导出匹配逻辑。

### 8.4 改动清单与验证
- 本 Bug 原则上**无代码改动**，先按上述 SQL 核实，产出核实结论。
- 若后续确认需"每标签取对应文件"而非"同文件多标签"，再评估导出匹配逻辑是否按 tag 维度独立匹配（当前实现已按 tag 精确匹配，数据正确时无问题）。
