### BUG-006 ❌ 公司筛选区补「资料完整状态」「具有开店资质」筛选项

**需求**：3.3.2 筛选区增加对应筛选项。

**现状（已核验）**：
- 前端 `getSearchFormItems`（`company/config/index.ts` L31-124）只有 9 个筛选项；`materialCompleteStatus`（L188）/`hasStoreQualification`（L198）仅是**表格列**，不是筛选。
- 后端 `CompanyPageDTO` 无这两个筛选字段；`pageCompany`（`CompanyServiceImpl` L65+）的 lambdaQuery 链未过滤。
- `materialCompleteStatus` 是**查询时计算的**（`CompanyManageServiceImpl` L209-216：公司文件标签是否含全部 system 必备标签 → "1"完整/"0"不完整），**不是数据库列**；`hasStoreQualification` 是 `cashier_company` 真实布尔列。

**改动步骤：**

**1. 后端 `CompanyPageDTO` 新增两个筛选字段：**
```java
@ApiModelProperty("资料完整状态筛选：0-不完整，1-完整（查询后二次过滤）")
private Integer materialCompleteStatus;

@ApiModelProperty("是否具备开店资质筛选：true/false")
private Boolean hasStoreQualification;
```

**2. 后端 `CompanyServiceImpl.pageCompany` 加 `hasStoreQualification` SQL 过滤（简单列）：**
```java
.eq(dto.getHasStoreQualification() != null,
        Company::getHasStoreQualification, dto.getHasStoreQualification())
```

**3. 后端 `materialCompleteStatus` 过滤（计算字段，推荐"预计算完整集 + IN 下推"）：**
由于完整性在查询后才算，不能直接在 lambdaQuery 里过滤，建议在 `CompanyManageServiceImpl` 分页前做两趟：
```java
// 仅当 materialCompleteStatus 筛选激活时：先按其它条件取全量 uniqueValue，算出完整公司集合，再 IN 下推分页
if (dto.getMaterialCompleteStatus() != null) {
    // 1) 用同一查询条件（去掉分页）查全部公司 uniqueValue
    // 2) 复用现有"文件标签→必备标签"计算逻辑，筛出完整/不完整的 uniqueValue 集合
    // 3) 分页查询时追加 .in(Company::getUniqueValue, 目标集合)
}
```
> 出纳公司数据量小（`EXPORT_PAGE_SIZE=100000` 级），两趟查询成本可接受。若接受"分页后二次过滤 + 修正 total"的近似做法也可，但分页跳页会有偏差，不推荐。

**4. 前端 `CompanySearchForm` 类型（`company/apis/type.ts` L281）追加：**

### BUG-008 ✅ 人员身份标识无法人/股东标记 —— 已核实为实时查询，无需改代码

**关键更正（已核实）**：V1.2.02 写"需确认 3.3.4 的法人/股东定期同步任务是否运行"——**代码里不存在该同步任务**，全后端 `@Scheduled` 0 个（`FileExpiryReminderJob` 为 xxl-job `@XxlJob`，仅管文件到期提醒）。身份标识是**查询时实时计算**：
- `EmployeeManageServiceImpl`（列表 `pageCashierEmployee` L119、详情 L164、导出 `listAllCashierEmployee` L309、下拉 `listCashierEmployees` L335）都调 `fillCompanyCounts`（L484）→ 读 `cashier_company`（法人，按 `legal_person_id`）与 `cashier_company_shareholder`（股东，按 `shareholder_id`，uniqueValue 去重）按 employeeId 统计 → `refreshIdentityTagsForList`（`EmployeeConvert` L138）生成「法人(N)」「股东(N)」标签。

**因此梁雪薇无"股东"标签，核实方向是数据关联，不是任务是否运行。** 执行核实 SQL：

```sql
-- 1) 查 test公司 的股东及其 shareholder_id（应为 bi-personnel 的 employeeId）
SELECT s.id, s.shareholder_id, s.shareholder_name, s.ratio, c.unique_value
  FROM cashier_company_shareholder s
  JOIN cashier_company c ON c.unique_value = s.unique_value AND c.deleted = 0
 WHERE c.company_name = 'test公司' AND s.deleted = 0;

-- 2) 查 bi-personnel 中该人员的 employeeId 是否存在
SELECT id, moniker FROM per_employee_file_head WHERE moniker = '梁雪薇' AND deleted = 0;

-- 3) 找出所有 shareholder_id 无法匹配到人员记录的股东（手动录入/未关联人员的）
SELECT s.unique_value, s.shareholder_name, s.shareholder_id
  FROM cashier_company_shareholder s
  LEFT JOIN per_employee_file_head e ON e.id = s.shareholder_id AND e.deleted = 0
 WHERE s.deleted = 0 AND e.id IS NULL;
```

**定性后的处理：**
- 若 `shareholder_id` 为 NULL（手动录入姓名）→ 该股东无法在"人员信息"中体现身份，属**数据录入方式**问题；如需人员维度可查，需要求新增公司时股东从人员下拉选择（`add.vue` 股东表选择 `shareholderOptions`，保存 `shareholderId = employeeId`）。
- 若 `shareholder_id` 有值但匹配不到人员 → 人员档案与出纳股东数据不一致，需核对 employeeId 来源。
- 若匹配正常但标签仍不显示 → 再查 `refreshIdentityTags` 的计数逻辑（`EmployeeConvert` L100-133：仅 `count>0` 才打标签）。

**验证**：修复关联数据后，人员列表"身份标识"列出现「股东」标签（多公司显示「股东(N)」）。

### BUG-009 ✅ 保证金阈值提示 —— 已简化：前端直接读缓存字典，删除专用 API 与后端日志

**原机制（已废弃）**：前端 `onMounted` 调专用接口 `/queryGuaranteeThreshold` 取阈值；后端保存时 `checkGuaranteeThreshold` 读字典打超阈值 `log.warn`。阈值字典未配时接口返回 null → 前端不弹提示 → 呈现"无数字/无提示"。日志无业务价值，接口属于"字典没进前端缓存"的补丁。

**简化改动（已实施）**：
- 前端 `DictionaryKey` 新增 `CASHIER_GUARANTEE_THRESHOLD`；`store/enum/index.ts` 新增对应枚举；`addOrEdit.vue` `onMounted` 改为直接读缓存字典 `CASHIER_GUARANTEE_THRESHOLD.list[0].one_id` 数值（未配置则保持 null，行为不变）。
- 删除前端 `queryGuaranteeThresholdApi`（`store/apis/index.ts`）。
- 删除后端 `StoreController.queryGuaranteeThreshold` 接口、`StoreManageServiceImpl.checkGuaranteeThreshold` 方法及 `validateStore` 中调用、`DictTypeConstants.CASHIER_GUARANTEE_THRESHOLD` 常量（Java 侧已无引用）。
- 净效果：少一个接口、少一次网络请求、少一段死日志，逻辑更直白。

**提示生效前提**：前端缓存字典 `CASHIER_GUARANTEE_THRESHOLD` 需由主应用字典下发且字典服务已配置该项数据（见第七节 ①），否则 `list` 为空、不弹提示——与原先字典未配时行为一致。
