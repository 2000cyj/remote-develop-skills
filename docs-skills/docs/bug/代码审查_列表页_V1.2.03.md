## 三、Bug 明细

### BUG-001 【中】银行卡导出未走 formatParams：日期范围筛选丢失 + 销户状态字符串致后端反序列化失败

- **页面**：银行卡列表
- **前端**：`src/pages/bankCard/index.vue:186`
- **后端**：`bi-cashier-api/.../dto/BankCardPageDTO.java:39`
- **问题**：列表查询在 `formatParams`（index.vue:48-70）把 `openDateRange`/`cancelDateRange` 拆成 `openDateStart/openDateEnd`、把销户状态字符串转成布尔 `isCanceled` 后才请求 `pageBankCard`；导出按钮把**原始 `searchForm`** 直接传给 `exportBankCardApi`，绕过了 formatParams。后端 `exportBankCard` 用 `@RequestBody BankCardPageDTO` 接收，`isCanceled` 是 `Boolean` 字段。
- **后果**：① 选了开户/销户日期区间筛选后导出，区间条件丢失；② 销户状态筛选为 `"canceled"` 时，Jackson 反序列化字符串到 `Boolean` 抛异常，导出 400 失败。
- **证据**：前端 index.vue:186 `:create-file-api-param="searchForm"`（ExportButton.vue:43-44 原样透传 → apis/index.ts:61-67 以 data 为 JSON body）；后端 BankCardPageDTO.java:39 `private Boolean isCanceled;`。对照：index.vue:48-70 formatParams 已做拆分与转换，导出路径完全没做。
- **修复**：导出前对 searchForm 复用与列表相同的字段转换（拆日期区间为 Start/End、isCanceled 由 `"canceled"/"active"` 转 true/false），再传入 `exportBankCardApi`。

### BUG-002 【轻】BankCard.id 前后端类型不一致：后端 Long 序列化为数字，前端声明 string

- **页面**：银行卡列表
- **前端**：`src/pages/bankCard/apis/type.ts:25`
- **后端**：`bi-cashier-component/.../po/BankCard.java:23-25`
- **问题**：type.ts 把 `id` 声明为 `id?: string`，注释称「后端 Long -> string 避免超过 MAX_SAFE_INTEGER」。但后端 BankCard PO 自身声明 `private Long id`（`@TableId(type=AUTO)`），**遮蔽**了 BaseEntity 上带 `@JsonSerialize(ToStringSerializer)` 的 id 字段，子类 getter 由 Lombok 生成在子类、无该注解，因此列表记录与 BankCardVO 的 id 在 JSON 里是**数字**而非字符串。
- **证据**：前端 type.ts:24-25；后端 BankCard.java:23-25（无 ToStringSerializer，BaseEntity.java:32-34 的注解被子类字段遮蔽）；对照 `pages/company/apis/type.ts:57`、`pages/store/apis/type.ts:46` 均声明 `id?: number`。
- **修复**：将 `BankCard.id` 类型改为 `number`，或在后端 BankCard PO/VO 的 id 字段补 `@JsonSerialize(using=ToStringSerializer.class)` 使声明与序列化一致。

### BUG-003 【轻】四个限额字段后端 BigDecimal 全局序列化为字符串，前端声明 number

- **页面**：银行卡列表
- **前端**：`src/pages/bankCard/apis/type.ts:56-62`
- **后端**：`bi-core/bi-starter-common/.../config/JacksonConfig.java:17-23`
- **问题**：后端 JacksonConfig 全局把 BigDecimal 序列化为字符串（`writeString`），且 `CashierApplication scanBasePackages=com.obo.*` 使该配置在出纳服务生效；因此列表返回的 `singleLimit/dailyLimit/monthlyLimit/yearlyLimit` 是 JSON 字符串（如 `"100.00"`），前端 type.ts 却声明为 number。
- **后果**：列表列 formatter 用 `Number(cellValue)` 包裹（config/index.ts:155-156）所以当前显示正常；但任何直接对 raw 值做数值运算的代码都会字符串拼接，属隐藏坑。
- **证据**：后端 JacksonConfig.java:17-23；CashierApplication.java:32 `scanBasePackages={"com.obo.*"}`；前端 type.ts:56-62。
- **修复**：前端将四个限额字段类型改为 string，或在取值处统一 `Number()` 归一化，与后端全局 BigDecimal→string 序列化对齐。

### BUG-004 【中】经营范围删除节点「已被引用」预警分支为死代码，永不触发

- **页面**：经营范围列表（树）
- **前端**：`src/pages/businessScope/index.vue:171`
- **后端**：`bi-cashier-api/.../vo/OperatingScopeTreeVO.java`
- **问题**：`handleDelete` 依赖 `node.businessScope` 判断「已配置经营范围描述（>50 字）可能已被引用，建议禁用而非删除」，但后端树形 VO（OperatingScopeTreeVO）**根本不含 businessScopeDescription 字段**，前端 `fillTreeNodeDefaults` 对所有节点硬编码 `businessScope=""`，导致 index.vue:171 的 if 分支条件永远为假，永远走普通删除确认。
- **后果**：用户删除被其他业务引用的节点时得不到任何预警，只能等后端抛「该经营类型已被使用，不可删除」。代码自相矛盾：`loadTree` 注释已承认「树 VO 不含 remark/businessScopeDescription，无法兜底」，却又在 handleDelete 中依赖该字段。
- **证据**：前端 index.vue:171 `if (node.businessScope && node.businessScope.length > 50)` 与 `utils/index.ts:22` `businessScope: ""`（fillTreeNodeDefaults 全部置空）；后端 OperatingScopeTreeVO 仅含 id/name/parentId/level/sort/children，`OperatingScopeManageServiceImpl.buildTree` 也只 set 这 6 个字段。
- **修复**：删除前先调 `queryOperatingScopeById` 获取真实 businessScopeDescription 再判断，或在 OperatingScopeTreeVO 中补充该字段并映射到节点。

### BUG-008 【中】公司开店资质 Switch 成功后不回写 row 也不刷新，开关弹回原状态

- **页面**：公司列表
- **前端**：`src/pages/company/index.vue:164-173`、`387-393`
- **后端**：`updateStoreQualification`（正常返回）
- **问题**：`hasStoreQualificationCell` 用 `:model-value` 单向绑定，`handleSwitchQualification` 成功分支只 `ElMessage` 提示，既不更新 `row.hasStoreQualification` 也不 `getList()`。el-switch 是受控组件（checked 由 modelValue 派生），父级不更新 modelValue 时开关视觉立即弹回旧值。
- **后果**：用户点击开关后看到状态弹回，以为操作无效并可能重复点击（实际后端已保存）。
- **证据**：前端 index.vue:387-393 `:model-value="..."` 单向绑定 + `@change`；index.vue:164-173 成功分支仅 `ElMessage.success`，未刷新；失败分支才 `getList()`。el-switch 源码 switch.vue.mjs:75 `checked = computed(() => actualValue.value === props.activeValue)`，模型值不更新则显示不变化。
- **修复**：`handleSwitchQualification` 成功时 `row.hasStoreQualification = val` 回写当前行（或调用 getList()），让开关保持新状态。

### BUG-016 【轻】店铺经营者搜索下拉仅加载前 30 条出纳人员

- **页面**：店铺列表
- **前端**：`src/pages/store/apis/index.ts:184-188`、`config/index.ts:69-80`

## 四、共性根因总结

| 根因 | 涉及页面 | 影响 |
|---|---|---|
| **导出直接传原始 searchForm，绕开列表的 formatParams 字段转换** | BUG-001 银行卡、BUG-007 公司、BUG-015 店铺 | 三个列表页都是「列表查询做了布尔/日期/数组转换，导出没做」，后端 Boolean 字段收到字符串反序列化失败、日期区间筛选丢失。**修复模式统一**：导出前对 searchForm 复用同一 formatParams 转换 |
| **前端类型声明与后端序列化不一致（类型以后端为准）** | BUG-002/003 银行卡、BUG-010/012 文件到期、BUG-014 印章 | id 的 number/string、BigDecimal 的 string/number、枚举 value/key、List\<String\> 的 string[]/number[]——当前多被 formatter 兜底掩盖，但会误导后续调用方 |
| **后端过滤字段缺失 / 查询条件不完整** | BUG-005 公司（industryCategory）、BUG-009 人员（导出筛选） | 前端传了但后端不接，筛选/导出静默失效，用户无感知 |

## 五、建议处理优先级

1. **导出必失败类（最高）**：BUG-001 / BUG-007 / BUG-015 —— 用户选中布尔/日期筛选后导出必然 400，三处同根因，建议统一改导出参数复用 formatParams，一并修掉。
2. **筛选/导出静默失效类（高）**：BUG-005（所属行业筛选后端不接）、BUG-009（人员导出筛选全失效）、BUG-006（法人下拉范围错误）。
3. **UI 状态错类（高）**：BUG-008（Switch 弹回）、BUG-011（表头全选未隐藏）。
4. **死代码/逻辑失效类（中）**：BUG-004（删除预警死分支）、BUG-013（指向不存在接口的 updateExpirationApi）。
5. **类型契约类（低，可随重构顺手）**：BUG-002 / BUG-003 / BUG-010 / BUG-012 / BUG-014 / BUG-016。
