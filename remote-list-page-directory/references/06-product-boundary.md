# 目标 6：判断规范 vs 产品 vs 业务事实

**适用场景**：某个改动是否在 skill 范围内？该不该由本 skill 直接下发？

> 这是**审查与重构目标的前置判断**。错误的边界判断会让 skill 越界变成"产品经理"或"代码风格警察"。

## 三类结论（强约束）

| 结论 | 定义 | 是否下发 | 何时下结论 |
|---|---|---|---|
| **必须整改（规范违规）** | skill 明确判定的不合规 | ✅ 直接下发 | 必须有规范原文/代码事实证据 |
| **建议优化（需需求确认）** | 不影响现有流程的改进空间 | ⚠️ 等用户确认 | 必须标注潜在影响 |
| **无需修改（已符合规范）** | 当前实现合规 | ❌ 不动 | - |

## 三类证据（必须区分）

| 证据类型 | 来源 | 可作为必须整改依据？ |
|---|---|---|
| **规范要求** | 本 skill 文档原文 + 项目规范 | ✅ 可以 |
| **代码事实** | 现有接口契约 + 现有代码约定 + 现有类型约束 | ✅ 可以 |
| **产品建议** | "我觉得应该..." / "其他系统都这样..." | ❌ 不可以 |

## 必须整改的证据要求

**必须**有下面任一证据才能判定"必须整改"：

1. **skill 文档明确禁止**：如"7 项目录名固定"——明确禁止不固定目录名
2. **现有契约/代码约束**：如后端接口要求 `uniqueValue` 必传——前端必传
3. **项目其他模块现状证据**：如 skill "标准参考实现"列出的 `src/pages/store/`——可作为现成事实

## 不可以判定必须整改的场景

- ❌ "页面应该有 Tab"—— 产品/UI 决策，无 skill 依据
- ❌ "状态分类不清晰，建议重新分"—— 产品/UI 决策
- ❌ "筛选入口太少"—— 产品决策
- ❌ "操作列按钮位置不对"—— UI 偏好
- ❌ "默认值应该是 X"—— 产品决策

> 即使 skill 加载了 `step_5.md` 等目录结构参考图，也**不等于** skill 要求做对应功能——目录图只说明结构，不强制 UI 内容。

## 建议优化的处理流程

```
1. skill 发现某处有改进建议（不是规范违规）
2. 标记为"建议优化（需需求确认）"
3. 在报告中标明：
   - 建议内容
   - 潜在影响（业务状态？查询条件？默认值？接口参数？权限？审批/删除流程？页面信息架构？）
   - 需要的用户输入
4. 不擅自实施
5. 用户确认后才能从"建议优化"升级为"必须整改"
```

## 错误边界举例

| 场景 | 错误判定 | 正确判定 |
|---|---|---|
| 列表页无 Tab | "必须新增 Tab"（产品建议） | "建议优化：Tab 缺失，潜在影响 X，需需求确认" |
| 某目录下文件名不规范 | "必须改名为 X" | "如 skill 有命名约束，则必须；否则无需修改" |
| 状态字段映射有偏差 | "必须重新映射" | "现有映射与后端是否一致？需查代码事实" |
| 文件未拆分 | "建议拆 3 个文件"（无业务依据） | "无需修改（除非业务复杂度达拆分阈值）" |
| 弹窗无壳模式违反 | "必须改造为弹窗无壳模式" | "必须整改"——skill file-responsibilities.md 明确禁止 |

## 边界争议的解决方案

如果发现某个改动**既像规范违规又像产品建议**：

1. 先用 skill 原文判断**是否违反规范**
2. 如违反规范 → 必须整改
3. 如不违反规范但有改进空间 → 建议优化
4. **不可同时判定两类**——一个改动要么违规、要么不违规

## 输出格式（边界判断结论）

```
## 结论分类：[业务模块名]

### 必须整改（X 项）
1. [违规] —— [证据：规范原文/代码事实] —— [整改建议]

### 建议优化（X 项，需需求确认）
1. [建议] —— [潜在影响] —— [需确认的内容]

### 无需修改（X 项）
1. [合规项]

### 不可判定的项（X 项，需更多输入）
1. [项] —— [缺什么证据]
```

## 反模式（不要做）

- ❌ 把"我觉得应该..."作为必须整改依据
- ❌ 不区分规范违规 vs 产品建议，下发前不分类
- ❌ 建议优化项不标潜在影响就直接实施
- ❌ 模糊处理（"建议但不强制..."——属污染）
